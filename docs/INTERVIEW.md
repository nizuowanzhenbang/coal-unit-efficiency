# 面试演示：有评估证据的燃烧优化建议

## 这次升级解决什么

旧实现用全部历史拟合后，再用同一批样本的 R² 生成“置信度”。它不能说明模型面对后来工况的表现；重复计算记录会放大样本量，样本不足重新 fit 时还可能沿用旧模型。

新版把模型选择、适用范围、降级与持久化证据放进已有建议生成流程：

1. 仅取当前工况之前、同一机组最近最多 500 个历史快照；每个快照只取最新能效结果，按时间升序排列。
2. 排除缺字段、非有限数和超出演示输入域的样本。每次拟合先清空旧模型。
3. 至少 24 条有效样本；前 80% 拟合，后 20% 留出验证。标准化参数只从训练部分计算。
4. 训练矩阵需满秩。验证 MAE ≤ 5 g/kWh，且相比“训练目标均值”基线误差改善超过 10%，才启用回归。
5. 留出样本不参与重新拟合。当前四个特征以及建议氧量必须在训练样本各维范围内，否则使用经验规则。
6. 将模式、原因、样本数、验证与基线误差、版本、系数、数据指纹、输入快照和历史快照 ID 随建议保存。以后新增数据不会改写旧建议的评估证据。

24 条、80/20、5 g/kWh 与 10% 是本原型显式声明的演示策略，**不是行业标准或生产验收结论**。输入域为负荷 (0,2000] MW、氧量 [0,21]%、排烟温度 [0,1000]℃、飞灰含碳量 [0,100)%、供电煤耗 (0,2000] g/kWh。当前负荷还须不超过配置容量。

## 页面上如何理解

- **验证模型**：用未参与训练的后段样本通过当前门槛。显示验证 MAE、基线 MAE 和评分。
- **经验规则**：样本不足、拟合退化、验证失败、工况越界或手动关闭历史。显示明确降级原因，评分显示“未验证”。
- **旧记录：未评估**：升级前的数据没有评估快照。新增 JSON 列允许 NULL，不伪造历史结果。
- `confidence` 为兼容旧 API 保留名称；新版含义为相对均值基线的误差改善评分，最高 0.95，经验规则为 0。它不是成功概率或统计置信区间。

氧量目标仍由既有经验负荷曲线决定，回归只用于估计氧量变化对应的煤耗差；飞灰项仍为经验修正。验证了历史煤耗预测并不等于验证了操作因果收益，更没有证明建议适用于真实炉型。训练区间检查仅逐特征进行，不证明联合分布覆盖。

## 五分钟面试路线

1. 按 README 在独立演示环境准备模拟数据，打开“燃烧优化建议与模型评估”。展开一条建议，讲清它使用什么依据、为什么降级。
2. 关闭“使用历史”，生成一条经验规则建议，检查页面标识与保存后的评估原因。
3. 运行以下测试，展示可重复的合成数据对比：稳定线性关系通过验证；后 20% 目标整体漂移 80 g/kWh 时失败；重复样本、NaN 和训练范围之外均得到明确处理。

```sh
cd backend
python -m pytest tests/test_optimizer_quality.py -v
python -m pytest tests/test_optimization_routes.py -v
```

4. 展示“改变留出标签不会改变已部署系数”的测试，解释如何避免验证数据泄漏。
5. 展示历史去重和排除当前/未来快照测试，再刷新列表说明评估记录已经落库。

## 常见追问

**为什么不用随机划分？** 运行数据具有时间相关性，时间留出更接近用过去预测后来的场景。一次划分仍有限，生产建模应增加滚动回测、负荷段评估、漂移监测和现场验证。

**为什么比较均值基线？** 模型复杂度必须带来可测量的改进。训练得分高但不如简单基线时，拒绝使用它。

**指纹能否重建训练集？** 指纹只能校验有效特征和目标值的有序数据是否一致；同时保存来源快照 ID、窗口和回归系数以便追溯。数据库被修改或删除后，仅指纹不能恢复数据，真实长期复现需数据版本化存档。

**为什么现在不接 MLflow/大模型？** 先让已有模型具有可验证的输入、评估和降级行为；后续可把这些证据接入模型注册与监控系统。这里尚未实现在线训练服务、自动调节控制或真实节煤收益验证。

**怎么升级旧库？** 启动初始化检查 `optimization_suggestions.evaluation`，缺失时新增可空 JSON 列。升级前备份并在维护窗口执行单实例初始化；SQLite 与 PostgreSQL 的 ALTER TABLE 会获取结构锁，本次没有实现多实例并发迁移协调。

## 简历表述

> 为电厂能效原型增加可复核的模型评估与降级机制，使用按时间留出的验证集对比均值基线，过滤异常样本并检查推断范围；持久化模型版本、样本指纹及评估指标，结合数据泄漏、漂移和历史去重测试验证完整流程。

所有演示均使用合成数据。建议采纳数、估算金额不能写成已经实现的真实节煤或财务收益。

## 输入与时间审计补充

每条建议固化当前特征、机组容量、煤低位热值、标煤价格、经验规则参数及输入 SHA-256；后续修改配置不会改写旧建议的计算依据。历史数据指纹与本次输入指纹分别保存。

新增工况时间在写入前统一为 UTC；无时区输入按 UTC 解释，避免 SQLite 丢失时区后把未来工况当作历史。旧数据库若曾混用时区，需要根据原始数据人工校正，系统不猜测历史时区。
